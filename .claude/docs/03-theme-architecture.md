## `functions.php` Breakdown

The entire file, in three parts.

### 1. Style enqueue — `anna_kalynyuk___norml_studio_theme_enqueue_scripts()`

Hooked to `wp_enqueue_scripts` at default priority 10.

| Handle | File | Purpose |
|---|---|---|
| `anna-kalynyuk---norml-studio-theme-parent-css` | `get_template_directory_uri() . '/style.css'` → Divi's `style.css` | Parent stylesheet |
| `anna-kalynyuk---norml-studio-theme-child-css` | `get_stylesheet_uri()` → child `style.css` | Child stylesheet — **empty** |

Two problems worth knowing before you touch this:

1. **No `deps` array.** The child handle does not declare the parent handle as a
   dependency, so load order is registration order rather than guaranteed. It happens
   to work; it isn't correct.
2. **Divi already enqueues its own stylesheet** as `divi-style`. This function
   re-enqueues Divi's `style.css` under a second handle, so the parent CSS is
   requested twice unless WP Rocket's minification collapses it. Because the child
   stylesheet is empty, the whole function is currently doing net harm rather than
   net good — but removing it is a real change with cache/RUCSS implications, so
   don't do it casually.

### 2. `[vertical_menu]` shortcode — `vertical_menu_shortcode()`

```php
[vertical_menu menu="Меню"]
```

Renders `wp_nav_menu()` with:

| Arg | Value |
|---|---|
| `menu` | `$atts['menu']` — **default `"Меню"`** (Cyrillic) |
| `container` | `div` |
| `container_class` | `custom-vertical-menu` |
| `menu_class` | `vertical-menu` |
| `echo` | `false` (returns, correct for a shortcode) |

Output structure: `.custom-vertical-menu > ul.vertical-menu > li…`

Notes:
- The default `"Меню"` matches the one menu that exists (term 2, slug `menyu`). Renaming that menu in wp-admin **silently breaks every use of this shortcode with no arguments.**
- There is **no CSS for `.custom-vertical-menu` or `.vertical-menu` anywhere in the project** — not in the child `style.css` (empty), not in the CodeKit SCSS. Either the styling is inline on the Divi module that hosts the shortcode, or this renders unstyled. Verify on the page that uses it before assuming it works.
- Uses `shortcode_atts()` — note that's the correct WordPress function name, so this is fine.
- Output is not escaped, but `wp_nav_menu()` escapes internally, so this is acceptable.

### 3. Gravity Forms AJAX filter — `filter_gravity_forms_force_ajax()`

Hooked to `gform_form_args`. Sets `$form_args['ajax'] = true` unconditionally, so
**every** Gravity Form on the site renders in AJAX mode regardless of how it was
embedded.

Consequence: form embeds do not need `ajax="true"`, and adding it changes nothing.
Conversely, if a form ever needs a full page reload on submit, this filter has to be
made conditional — there is currently no escape hatch.

### Nothing else

No `add_theme_support()`. No `register_nav_menus()`. No `register_sidebar()`. No
`add_image_size()`. No CPT or taxonomy registration. No AJAX handlers. No REST routes.
No `do_action()` / `apply_filters()` of its own. No included files.

|---|---|---|---|
| `wp_enqueue_scripts` | action | `anna_kalynyuk___norml_studio_theme_enqueue_scripts` | 10 |
| `gform_form_args` | filter | `filter_gravity_forms_force_ajax` | 10 |

| Shortcode | Callback |
|---|---|

## The CSS layer — CodeKit, not the theme

**This is the project's most important non-obvious convention.**

Custom CSS does **not** live in the theme. It lives in the database as `custom-code`
posts managed by the CodeKit plugin (`wp-admin → Custom Codes`), which compiles each
one to files in `wp-content/custom_codes/`.

### The two custom codes

| ID | Title | Language | Location | Saves | State |
|---|---|---|---|---|---|
| 1907 | `Public Side SCSS` | scss | frontend | 8 | active, has content |
| 1908 | `Admin Side SCSS` | scss | backend | 0 | **never saved — empty** |

Meta keys per code: `_codes_language`, `_codes_location`, `_codes_adminroles`
(empty array), `_codes_savecount`, `_codes_show_breakpoints`.

### Compiled output on disk

```
wp-content/custom_codes/
├── 1907-scss-desktop.scss    # 262 B — SOURCE (the "xl / desktop" breakpoint)
├── 1907-scss-output.scss     #  62 B — intermediate
└── 1907-scss-output.css      # 566 B — COMPILED, this is what loads
```

`_codes_show_breakpoints: 1` means CodeKit exposes per-breakpoint source files; only
the `desktop` one has been used, so there is one source file rather than a set.

### What the entire frontend SCSS actually contains

```scss
@import url('https://fonts.googleapis.com/css2?family=Nunito+Sans:opsz,wght@6..12,300;6..12,400;6..12,600;6..12,700&display=swap');
.page-id-2133 {
	.rw-google-widget__top{
		    background: transparent!important;
		--widget-bg-color: transparent!important;
	}
}
```

That is all of it: a Google Fonts import plus one override that makes the Review Wall
Google widget's header transparent on page 2133 (`Відгуки` / Reviews).

Two things follow:
- **The site's visual design is ~100% Divi module settings**, not stylesheets. Changing a colour or spacing almost always means editing a Divi module, not writing CSS.
- The `@import` here is the **second** Google Fonts request for Nunito Sans (Divi makes the first). A CSS `@import` is also the slowest possible way to load a font — it serialises behind the stylesheet.

### How to add CSS (the correct workflow)

1. `wp-admin → Custom Codes → Public Side SCSS` (post 1907)
2. Edit the SCSS in the plugin's editor and save — the plugin recompiles to `1907-scss-output.css`
3. Purge WP Rocket cache **and** clear the RUCSS store (Remove Unused CSS is on; it will otherwise strip your new rules)
4. Purge `wp-content/et-cache/` if the change interacts with Divi's dynamic CSS

You *can* edit `1907-scss-desktop.scss` on disk, but the compiled `.css` will be stale
until you re-save the code in wp-admin. **Never hand-edit `*-output.*`** — the next save
overwrites it.

## Template Hierarchy

The child theme provides **zero** template files. Resolution order for every request is:

1. Divi Theme Builder assignment (checked first, and it wins) → see below
2. `wp-content/themes/anna-kalynyuk---norml-studio-theme/{template}.php` → **never matches, nothing exists**
3. `wp-content/themes/Divi/{template}.php` → always the actual answer

## Build Pipeline

- **Package manager:** none — no `package.json`, no `composer.json`, no lockfile
- **Build tool:** none in the repo. The only compile step is **CodeKit's server-side SCSS compiler**, which runs inside WordPress on save.
- **CSS processing:** SCSS → CSS, by CodeKit, in the database → written to `wp-content/custom_codes/`
- **JS bundling:** none
- **Build command:** n/a — "build" means clicking Save in `wp-admin → Custom Codes`
- **Watch command:** n/a
- **Source directory:** `wp-content/custom_codes/*-desktop.scss` (outside the theme)
- **Output directory:** `wp-content/custom_codes/*-output.css` (outside the theme)

Note that the source and the output both live **outside** the theme, in
`wp-content/custom_codes/`. A theme-only deploy therefore does not carry the site's
CSS. Anything that deploys this project must account for `wp-content/custom_codes/`
and for the `custom-code` posts in the database.

## Coding Patterns and Conventions

Observations, with the caveat that there are only ~40 lines of PHP to observe.

- **Function naming:** `anna_kalynyuk___norml_studio_theme_*` for the enqueue (prefixed from the text domain, with the triple underscore that comes from the theme slug's `---`), but `vertical_menu_shortcode()` and `filter_gravity_forms_force_ajax()` are **unprefixed globals**. Inconsistent, and the unprefixed names are a collision risk.
- **PHP standard:** WordPress style (snake_case, 4-space indent, `add_action` at file scope). One function has a docblock; the others have none.
- **Escaping / sanitisation:** relies on `wp_nav_menu()`'s internal escaping. No explicit `esc_*` calls. Acceptable at this size, but there is no established pattern to follow if the file grows.
- **i18n:** none. Text domain declared, never loaded, never used. A Cyrillic string (`'Меню'`) is hardcoded as a default.
- **CSS methodology:** none — the project has effectively no stylesheet. The 7 lines that exist use SCSS nesting plus `!important` scoped by a WordPress body class (`.page-id-2133`). Page-ID-scoped `!important` overrides are the de facto convention.
- **JS patterns:** none in the theme. Site JS is Divi's jQuery-based bundle, moved to `<body>` and deferred by WP Rocket.
- **File organisation philosophy:** flat and minimal by design. **The architecture decision this project has already made is "build in Divi, not in code."** Respect it or change it deliberately — don't drift.

## How to do common tasks

Given the above, the honest answers:

**Add a new page template** — don't create a PHP file; it won't be reachable. Create a
Divi Theme Builder template in `wp-admin → Divi → Theme Builder` and set its
`_et_use_on` assignment there.

**Change the header** — edit Divi header layout **284**, then apply the same change to
**2213** and **2214**, or single posts and category archives will diverge. Consider
consolidating to one header layout as a deliberate cleanup.

**Change the footer** — edit Divi footer layout **365**. One place, all pages.

**Add a custom post type** — no existing pattern to follow (the theme registers none).
Add it to the child `functions.php` with a proper prefix, and record the decision in
`changelog/daily.md` as `[DECISION]`, because it is the first CPT the theme owns.

**Add editable structured fields** — there is no field layer. Either author in Divi, or
introduce ACF as an explicit architectural decision.

**Add CSS** — `wp-admin → Custom Codes → Public Side SCSS` (post 1907), then purge WP
Rocket **and** the RUCSS store. Never the child `style.css`.

**Add a script or style via PHP** — extend the existing `wp_enqueue_scripts` callback in
`functions.php`, and add a proper `deps` array while you're in there.

**Add a shortcode** — follow `vertical_menu_shortcode()`'s shape, but prefix the
function name (`ak_` or similar) rather than copying the unprefixed style.

**Change site colours or type** — almost certainly `wp-admin → Divi → Theme Options`
(the `et_divi` option), or the individual Divi module. Read `../design.md` first — it is
binding.
