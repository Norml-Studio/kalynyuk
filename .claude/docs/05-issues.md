## Critical

### The primary navigation on PRODUCTION is an auto-generated page list, not the curated menu
> **Found 2026-07-27 during phase 0**, by rendering production with Playwright and
> walking the DOM ancestry of a nav link. Present on production AND local — not a
> local artifact.
> **ROOT CAUSE CORRECTED 2026-07-27** during the phase-1 header build. The original
> entry blamed *"a Divi `et_pb_menu` module with no menu assigned"*. **That was
> wrong.** The module had a menu assigned; **Polylang was nullifying the location.**
>
> `polylang/src/frontend/frontend-nav-menu.php:244`:
> ```php
> $menus[$loc] = empty($options['nav_menus'][$theme][$loc][$curlang->slug]) ? 0 : …;
> ```
> Polylang **overwrites every menu location with `0`** on the front end unless that
> location has an explicit per-language assignment — and `polylang.nav_menus` was an
> empty array. So `primary-menu` resolved to 0 in every language, `wp_nav_menu()`
> found no menu, and fell back to `wp_page_menu()`. Proven by building a new header
> that reads the location directly: it rendered an empty nav until the per-language
> assignment was written, then rendered all 8 items.
>
> **Status: FIXED, two ways.** Data: `polylang.nav_menus[{theme}]['primary-menu']['uk'] = 2`.
> Code: `ak_nav_menu_location_fallback()` in `inc/nav.php` (filter
> `theme_mod_nav_menu_locations`, priority 30 — after Polylang's 20) makes any
> language without its own assignment inherit the **default language's** menu, so a
> newly added language never ships an empty header.
- **What:** the visible header nav was an auto-generated page list — `li.page_item` items under `ul.et-menu.nav → div.et_pb_menu__wrap`, i.e. `wp_page_menu()` output inside Divi's menu module. It rendered **12 items wrapping onto three lines**: `FAQ · Feedback · Portugal · Блог · Відгуки · Головна · Довіра · Калькулятор · Політика конфіденційності · Послуги · Про мене · Іпотека`.
- **Where:** `polylang` option (`nav_menus`), surfaced through Divi header layouts 284 / 2213 / 2214; was visible on `https://www.kalynyuk.com/`
- **Why it matters:** three of those entries should never be in primary nav — `Feedback` (150 B, orphaned), `Portugal` (448 B, orphaned) and `Політика конфіденційності`. A twelfth entry, `Іпотека → /category/ipoteka/`, is a **category archive**, not a page. The curated 8-item menu (`Меню`, term 2, assigned to `primary-menu`) is not what visitors see. The IA the client signed off on is not the IA that shipped, and the nav is visibly broken across three lines at 1440px.
- **Compounding:** `[vertical_menu]` **does** render the correct 8-item menu (`ul.vertical-menu`, 16 `li.menu-item` = 8 × desktop+mobile), but its output has **no CSS anywhere in the project** (see the related Warning below), so the correct menu is on the page, unstyled and orphaned, while the wrong one is the one that displays.
- **Fix scope:** phase 1 (custom header) resolves all of this at once. Do not patch the Divi module — it is being deleted.

### Two published pages are completely empty and indexable
- **What:** `Головна - English` (ID 2484, `en`) and `Головна - Русский` (ID 2485, `ru`) have `post_content` of **0 bytes**, `_et_pb_use_builder` off, and status `publish`.

### Header layout is triplicated with no shared source
- **What:** Three near-identical `et_header_layout` records — 284 (50,667 B), 2213 (50,318 B), 2214 (50,318 B) — serve the default template, category archives, and single posts respectively. 2213 and 2214 are the same byte length; 284 differs by 349 B. All three are titled `All Category Pages`, so their names carry no information.
- **Where:** `et_header_layout` posts 284, 2213, 2214; assigned via `et_template` 291, 2159, 2190
- **Why it matters:** Any header change must be repeated three times. It will not be, and the three will drift — a nav item, phone number, or logo change silently applying to pages but not posts. The identical misleading titles make it likely an editor will edit the wrong one. This is the highest-probability future-breakage point in the project.

### ~95 KB of calculator CSS is duplicated byte-for-byte across two pages
- **What:** Two `et_pb_code` module bodies are md5-identical on the homepage and the calculator page — 75,257 B (`23c2cf38ffe4`) and 22,186 B (`2a345770b16f`).

- **Why it matters:** No shared source exists, so the two copies can only be kept in sync by hand. It is also the direct cause of the database bloat below: every builder save on either page re-serialises the whole blob into a new revision.

### 79% of the database is post revisions
- **What:** `wp_posts` is 176.7 MB of a 193.8 MB database. 1,356 revisions hold **153.3 MB** of `post_content`; all real content combined is **0.98 MB**. The homepage alone has **516 revisions / 107 MB**; the calculator has **434 / 35.8 MB**.
- **Where:** `wp_posts`; `WP_POST_REVISIONS` is **not defined** in `wp-config.php`
- **Why it matters:** Backups, migrations, and DB imports move ~150× more data than the site contains. UpdraftPlus runs a daily database backup against this. It slows every `wp db export`, every staging refresh, and every restore, and it inflates hosting storage indefinitely because nothing caps it.

### Production access cannot be resolved

### No version control
- **What:** Neither the theme nor the WordPress install is a git repository. There is no `.git`, no `package.json`, no lockfile, and no Bitbucket remote recorded anywhere.
- **Where:** `f:\localsites\kalynyuk.loc` and the theme root
- **Why it matters:** There is no history, no diff, no rollback, and no review gate for the only code the project owns. Combined with the fact that most of the site lives in the database, a bad Divi save or a bad CodeKit save is recoverable only from an UpdraftPlus backup.

### Web-reachable stale PHP files in `wp-content/`
- **What:** `advanced-cache-backup.php`, `advanced-cache.php-old`, `index.php-old` sit in `wp-content/` alongside the live `advanced-cache.php`.
- **Where:** `wp-content/`
- **Why it matters:** `*-old` and `*-backup` files are not parsed as PHP by Apache in the `.php-old` case, which means their **source is served as plain text** on request — leaking whatever the old cache drop-in contained. The `-backup.php` file *is* executable and reachable directly. Neither should exist in a web root.

### API keys and OAuth tokens for uninstalled plugins remain in the database
- **What:** `review_wall_api_key` (36 chars, live plugin), plus `elementor_connect_site_key` (32), `depicter_client_key` (32), `frm_connect_token` (128), and `updraftplus_tmp_googledrive_access_token` — the middle three belong to plugins that are no longer installed.

- **Why it matters:** Credentials for third-party services persist in a database that gets exported to staging and into daily backups, with no plugin left to rotate or revoke them. Anyone with DB or backup access holds them.

### Google Fonts loaded twice, one of them via CSS `@import`
- **What:** Nunito Sans (weights 300/400/600/700) is requested from `fonts.googleapis.com` by Divi's own font enqueue **and** again by an `@import url(...)` at the top of the CodeKit SCSS. WP Rocket's `host_fonts_locally` is `0`.
- **Where:** `et_divi` (`body_font` / `heading_font`); `wp-content/custom_codes/1907-scss-desktop.scss` line 1 → compiled into `1907-scss-output.css`
- **Why it matters:** Two render-blocking third-party requests for the same font. A CSS `@import` is the slowest available mechanism — it cannot start until the containing stylesheet has downloaded and parsed, so it serialises the font behind CSS. On a site where performance is otherwise heavily engineered (RUCSS, defer-all-JS, preload), this is a self-inflicted regression.

### Browser caching and compression are not configured
- **What:** `.htaccess` contains only the stock WordPress rewrite block plus an **empty** Really Simple Security marker (the directory-indexing rules were never written). WP Rocket's usual `mod_expires` / `mod_deflate` / gzip block is absent entirely.
- **Where:** `f:\localsites\kalynyuk.loc\.htaccess`
- **Why it matters:** No `Expires`/`Cache-Control` headers and no gzip/deflate at the server level, so every asset is re-fetched and sent uncompressed. WP Rocket normally writes these rules on activation; their absence suggests either a write-permission failure or that something stripped the file. Worth confirming on production — if the same is true there, the whole caching plugin is doing half its job.

### Image lazy-loading is disabled while heavy performance features are on
- **What:** WP Rocket has `lazyload: 0` and `lazyload_iframes: 0`, while `remove_unused_css: 1`, `defer_all_js: 1`, `preload_links: 1`, `manual_preload: 1` are all on.
- **Where:** `wp_rocket_settings`
- **Why it matters:** An inconsistent optimisation posture — the aggressive, breakage-prone features are enabled and the safe, high-yield one is off. On a 9-section homepage with 17 image modules this is the cheapest available win left on the table, so its absence is more likely an accident than a decision.

### Remove Unused CSS on a Divi site, plus deferred JS behind a JS preloader
- **What:** `remove_unused_css: 1` against Divi's dynamically generated per-page CSS; `defer_all_js: 1` combined with `divi_enable_jquery_body: on` and an active full-page JS preloader (`the-preloader` 2.0.2).
- **Where:** `wp_rocket_settings`, `et_divi`, `the_preloader_settings`
- **Why it matters:** Two independent fragility sources. RUCSS rewriting Divi's dynamic CSS is the standard cause of "styles missing on one page only" — and the RUCSS store (`wp_wpr_rucss_used_css`) is the first place to clear when that happens. Separately, a preloader can only remove itself once its own JS executes, which deferral delays; a JS error leaves the overlay permanently covering the site.

### Five cron jobs run every 60 seconds on DB-driven cron
- **What:** `action_scheduler_run_queue`, `action_scheduler_run_queue_rucss`, `rocket_saas_on_submit_jobs`, `rocket_saas_pending_jobs`, `rocket_preload_process_pending` are all on a 1-minute recurrence. `DISABLE_WP_CRON` is not set, so they are triggered by page views. 51 cron events total.
- **Where:** `cron` option (8.4 KB, autoloaded)
- **Why it matters:** On a low-traffic site the queue backs up; on a busy one every visitor pays a share of the work. Four of the five belong to WP Rocket, so the performance plugin is itself a recurring per-request cost.

### ~~The theme re-enqueues the parent stylesheet under a second handle~~ — CORRECTED + FIXED
> **Corrected 2026-07-27 during phase 0.** The original entry claimed the *parent*
> stylesheet was requested twice. That was **wrong**. Established by reading
> `Divi/functions.php:381-393` and by rendering the site in both states.
- **What actually happened:** the old callback enqueued the parent `style.css` under its own handle plus the child `style.css` with no `deps`. Divi's `et_divi_enqueue_stylesheet()` picks its branch by regex-testing whether the child already enqueued a parent `style*.css`. WordPress loads the **child** `functions.php` first, so the child's priority-10 callback won that race, pushed Divi into its *"the child already did it"* branch (line 387), and Divi then enqueued `divi-style` pointing at the **child's** `style.css`. The duplicated file was therefore the **child's** (empty) stylesheet — not the parent's. Load order was also registration-order luck rather than declared.
- **Where:** `functions.php` (pre-migration), `Divi/functions.php:381-393`
- **Status: FIXED.** [inc/assets.php](inc/assets.php) enqueues **neither** stylesheet, letting Divi take its intended branch and load both itself, once. Our CSS is enqueued at priority **20** — after Divi has registered `divi-style` — with a conditional dependency on it, so cascade order is declared rather than accidental. Measured on the local homepage: `style.css` sat at stylesheet index 16 before the fix, 15 after. One redundant request removed.
- **Still open, related:** `et-cache/global/et-divi-customizer-global.min.css` loads **after** our `dist/css/main.css`. It is Divi-selector-scoped so it does not collide today, but any header/footer rule sharing a Divi selector will lose to it. Watch for this in phase 1.
